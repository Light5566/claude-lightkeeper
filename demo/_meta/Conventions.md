# Conventions

How notes in this vault are written. A note that doesn't follow this is a bug. Fix it.

## The one rule that matters

> **Every `[[link]]` carries a reason.**

```markdown
- [[Invoice]] — an order confirmation bills through `InvoiceService::create()`
```

not

```markdown
- [[Invoice]]
```

A bare link makes the graph a hairball. You can see that two things touch but not how, so the picture tells you nothing you couldn't have guessed. The reason clause turns it into a map you can navigate. It is also the part that rots first: when the reason stops being true the link is a lie, and that is your signal to fix the note.

The machine index reads the reasons too. They become the "blast radius" printed beside every `vault find` hit, so a bare link also hides a relationship from the tooling.

## Folders

| Folder | Holds | One note per |
|---|---|---|
| `1 Domains` | Business areas, grouped the way the product groups them (navigation, route groups) | Area |
| `2 Modules` | The citizens of the world: a feature you can point at in the UI or the API | Module |
| `3 Flows` | End-to-end journeys that cross several modules | Journey |
| `4 Integrations` | Anything outside the codebase that it talks to | External system |
| `5 Platform` | Cross-cutting mechanics every module inherits, and traps that bite again | Convention or trap |
| `6 Decisions` | Why something is the way it is, decision-record style | Decision |
| `7 Releases` | Which parts of the world moved in a version | Version |
| `8 Repos` | Orientation for one codebase | Repo |
| `_templates` | Copy these to start a note | — |
| `_meta` | Conventions, How to update, `vault.json`, optional `local.md`, the generated files, `views/` | — |

`Home.md` and `World.canvas` sit at the root. The canvas is regenerated by `vault check --write`. Never edit it by hand.

Domains follow the product. Take them from the navigation or the route groups, and when the product regroups, the domains follow. Don't invent a parallel taxonomy.

## Frontmatter

Every note carries these. Obsidian renders them as properties; the tool reads them line by line.

| Key | Values | Why it exists |
|---|---|---|
| `type` | `module` `domain` `flow` `integration` `platform` `decision` `release` `repo` `meta` | Filtering, graph colour, the views |
| `aliases` | `[Billing, INV]` — a flat inline list | Other names this note answers to. `[[INV]]` resolves, `vault find` matches them, and the prompt hook watches for them |
| `status` | `shipped` `in-progress` `planned` `deprecated`; decisions use `accepted` `open` `superseded` | A note about unmerged work must say so, or the vault lies about production |
| `depth` | `full` `stub` | Honest coverage. A stub is a real note with real links, just thin |
| `repo` | A key from `repos` in `vault.json`, or `both` | Where the code is |
| `domain` | The name of a `1 Domains` note | Groups modules |
| `since` | `v1.4.0` | The release it first shipped in, when known. Leave it empty rather than guess |
| `updated` | `YYYY-MM-DD` | The staleness detector. Bump it every time you touch the note |
| `flags` | `[FEATURE_X_ENABLED]` | Every flag-gated thing at a glance; the prompt hook matches these too |
| `tags` | `[module, domain/billing]` | Tag-pane navigation |

Frontmatter stays **flat, one `key: value` per line**. Lists are inline: `flags: [A, B]`. Nested YAML parses wrong in the tool and in Obsidian's queries.

### What `status` means

**`shipped` means the code is on the production branch**: the `production_ref` of that repo in `vault.json`, typically `origin/main`. Work that exists only on a staging branch or a feature branch is `in-progress`, however finished it feels.

Verify, don't assume:

```bash
git merge-base --is-ancestor <sha> origin/main && grep -rn "the thing you expect" app/
```

The content grep matters. A commit in the production branch's history is not proof the feature is live; it may have been reworked away later.

`status` and `depth` do different jobs. `status: in-progress` means the code isn't on production. `depth: stub` means the note is thin. A shipped module with a stub note is the normal starting state.

### Alias rules

`vault check` enforces these.

- A flat one-line list only.
- Aliases are other names and abbreviations of **this** note: what the team, the client or the code call it. Never a related-but-different concept; that is a link's job.
- No `[[`, `]]`, `|` or `#` inside an alias.
- An alias may not collide with another note's name or alias.

## Section order

Module and integration notes always use this order, so any two diff cleanly and you learn where to look:

1. **What it is** — plain language, two or three sentences
2. **Where it lives** — the paths table
3. **How it works** — in the order the code runs
4. **Connects to** — linked, with reasons
5. **Config & flags**
6. **Gotchas**
7. **History**

Don't add sections. If something doesn't fit, it belongs in *Gotchas* or in its own `6 Decisions` note.

## Writing style

- **Paths are code-spans, not links**: `app/Services/PaymentService.php`. The vault points at code; it isn't a code browser.
- **The *Where it lives* table is machine-read**, so it must be true. Real files only. The first path in a cell is fully qualified; siblings in the same cell may be bare filenames. **Never cite a container directory** such as `app/Services/` there. Delete a row you can't fill.
- **Only the owning note cites a file by its full path.** Every full path in a note's body counts as ownership in the index, so a flow, platform or decision note that writes `app/Services/PaymentService.php` starts competing with the Payment note for that file in the pre-edit hook. Elsewhere, name the code by class and method: `PaymentService::capture()`. It reads just as well and claims nothing.
- **Plain language in *What it is*.** If a non-engineer can't follow it, rewrite it. Everything technical has six other sections to live in.
- **Gotchas are specific.** "Be careful with totals" is worthless. "`Order::total()` returns minor units and the CSV export multiplies by 100 again if you hand it a float" is worth keeping forever.
- **Say what the code does, not what someone remembers.** When the why of a deliberate-looking choice isn't recorded anywhere, write "reason not recorded". A wrong why is the one thing the vault can never recover from.
- **No screenshots.** They rot faster than text.

## Stub → full

A stub gets promoted the first time you touch that module for real. Promotion means: fill *How it works*, add at least two reasoned links, list the real gotchas, set `depth: full`, bump `updated`. Don't promote by padding. A stub that is honestly thin beats a full note that is half invented.

## Machine index

The vault is read by machines as well as people. `vault find` and the Claude Code hooks run off `_meta/index.json`, which `vault check --write` rebuilds and which is gitignored on purpose: the Stop reminder goes quiet while the vault is dirty, so a tracked, auto-rebuilt index would silence it for good.

What the index extracts, and therefore what your writing feeds:

- the **Where it lives** table → the file-to-note reverse lookup behind the pre-edit hook and `vault find --paths`. Container directories are ignored and reported by `vault check`.
- reasoned `- [[link]] — why` bullets, and the `See [[X]] — why` idiom → the edge list whose reasons become the blast radius beside every hit. One more reason the one rule matters.
- the first sentence of **What it is** → the one-liner shown in search results.
- `aliases` and `flags` → extra search names, and what the prompt hook matches on.
- `updated`, `depth` and `status` → the honesty fields printed with every hit, and the inputs to `Coverage.md`, `Attention.md` and the views.

## What does NOT go here

- **Code.** Snippets only where the shape itself is the point.
- **The release log.** The repo's `CHANGELOG.md` (or whatever `version_log` names in `vault.json`) owns release history and deploy commands. `7 Releases` only records which parts of the world moved.
- **Secrets, credentials, personal data.** No keys, tokens or passwords. No real names, emails, phone numbers or account identifiers; use obvious placeholders. The vault syncs to other machines.
- **Task lists.** Those live in your tracker.
- **Docs with an external audience.** Client guides, runbooks and API references stay in the repo's docs folder. The vault links to them rather than absorbing them.

Rules that apply only to this vault go in `_meta/local.md`. Every skill reads it last, so it is the right place for a house style, a naming rule or a branch convention that this file doesn't cover.
